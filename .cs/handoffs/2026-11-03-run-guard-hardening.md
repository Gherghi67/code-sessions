# Handoff: run-guard hardening (R1 + D2 from PR #25's review)

## Primary Request and Intent

The grumpy review of PR #25 (the v2026.11.1 upstream sync, merged into fork main as e08999ee) raised findings the
user chose to move out of that PR into one follow-up PR on Gherghi67/code-sessions:

- **R1:** `cs_run_guarded` opens `.cs/local/run-lease.guard` with `exec 9> "$meta/local/run-lease.guard"`. A symlink
  (or other non-regular file) planted at that path is followed, and the shell's O_TRUNC truncates the link's target.
  The session directory, `/tmp` and `$TMPDIR` are agent-writable (memory `project_codex_sandbox_trust_boundary`), so a
  sandboxed engine can plant that link and make cs truncate a file it could not write itself.
- **D2:** `_CS_LOCK_LIVE_PID` in `_take_session_lock` (lib/15-lock.sh) is assigned but no caller reads it. Its only
  caller, `cs -encrypt` (lib/63-encrypt.sh:199), says "the session is live" without a pid.

Ship both as one PR from `cs/run-guard-hardening`, cut from `github/main` e08999ee.

## Key Technical Concepts

- `cs_run_guarded` (lib/02-shared.sh:1204, folded by build.sh into bin/cs and copied to hooks/cs-shared.sh:1206)
  serialises ownership changes on a **persistent inode**. Waiters must all lock the same inode, so the guard is never
  unlinked. Locking is `flock -w 5 9` on Linux, `lockf -s -t 5 9` on macOS. The descriptor belongs to the subshell,
  so the kernel releases it even after SIGKILL.
- Because the inode must persist, the fix cannot be "unlink and recreate". What the review suggested:
  - refuse a symlink or a non-regular file at the guard path;
  - open without O_TRUNC (`exec 9>>` append, or `exec 9<>` read-write, as `_cs_lock` already does at
    lib/02-shared.sh:~560);
  - after the open, check that the opened fd's inode is the path's inode, so a swap between the check and the open is
    caught. On macOS, `stat -f %i` on the path and on `/dev/fd/9` works. On Linux, use `stat -L -c %i /proc/self/fd/9`
    or `/dev/fd/9`. Perl is already a dependency of the lock code (`_require_session_lock_perl`), so `perl -e
    'stat(...)'` comparing dev+ino on a dup'd fd is a portable option.
- `umask 077` is set around the open so the guard is private. Keep that.
- `cs_run_guarded` is fork-only. Upstream hex/claude-sessions has no run lease, and `git grep cs_run_guarded
  origin/main -- lib` is empty. Upstream's `_CS_LOCK_LIVE_PID` *is* read (origin/main lib/15-lock.sh:204,
  `1) lock_pid="$_CS_LOCK_LIVE_PID"`). In the fork it became write-only when acquire_session_lock was rewritten
  around the guard.
- `.cs/local` is created through `cs_mkdir_inside`, which already refuses a link out of the session.

## Problem Solving

- An ordinary `exec 9>` on a fresh path creates the file, and that must still happen for a new session. The refusal
  applies only when the path exists and is not a regular file, or is a symlink.
- A TOCTOU window remains between the `-L`/`-f` check and the open. The post-open inode comparison closes it: if the
  inode differs, close fd 9 and refuse. Without O_TRUNC, a race at worst opens the target in append or read-write
  mode and writes nothing, so it does no damage.
- hooks must exit 0 (memory `project_codex_sandbox_trust_boundary`). A refusal inside a hook path must keep that
  contract. Check hooks/session-end.sh's `|| true`.
